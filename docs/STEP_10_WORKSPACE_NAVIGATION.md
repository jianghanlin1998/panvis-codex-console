# Step 10 — project workspace and task navigation

Approved scope: make projects, big tasks and subtasks visibly related; expose context and a dependency-based progress view; allow conversational draft creation and selectable review depth; provide a persistent macOS desktop entry. Board content changes and the next live task are reserved for the owner's next Console session.

## Resulting behavior

- The sidebar follows Project → Big Task → Subtask. Active projects initially expand; ended projects collapse into the lower group. Completed big tasks collapse in place and retain progression order. Manual folding survives refresh; navigating to a different descendant reveals its ancestors. Earlier attempts remain accessible separately from the delivered result.
- Project progress shows dependency arrows, branches and joins, role/stage and completion. Same-column nodes are logically parallel opportunities. The executor still dispatches serially; readiness is not represented as active execution.
- Project, task and subtask discussions have separate histories. Confirmed parent conclusions are inherited with source labels. A conversation-created draft links back to the actual saved originating message. Previous Codex conversations were not stored as Console transcripts; explicitly approved conclusions may be curated as attributed context without fabricating messages.
- Chat actions create direction drafts and suggested subtasks, set scope defaults, or adjust selected review profiles on a plan that has not been approved for execution. Direction and execution approval remain owner decisions. Applying a profile amendment creates a separate immutable plan version, runs a fresh Reviewer and retains the original records and cumulative planning usage. Approved execution cannot be silently rewritten.

## Local entry and recovery

After building, `node scripts/install-desktop-entry.mjs` installs `~/Desktop/Codex Task Console.app`. Double-clicking starts or reuses the local daemon and opens the browser through a one-use ticket. The entry has a stable name; the internal local port remains ephemeral. No hosted deployment or login service is introduced. Closing the browser does not stop the daemon. Reopening after a computer restart starts it again; interrupted work remains recorded and requires the existing recovery decision.

Desktop activation is now verified. The original app lacked a bundle identifier and exited immediately after detaching Node; its startup repeatedly hit EPERM while reading the repository entrypoint. The installer now assigns a stable app identity, probes access while the responsible app remains alive, adds a Documents usage explanation, uses a stay-open applet with a reopen handler, and signs/verifies the completed local bundle. Failure of the foreground probe displays a clear message. No system privacy settings or protected-access database were modified. ### Reopening correction after owner reproduction

The owner subsequently reproduced an unresponsive desktop icon. The daemon stayed healthy, with no new startup log entry. The leftover asynchronous `cd && nohup ...` shell still held both applet capture pipes; AppleScript therefore remained inside its first launch call and could not handle subsequent reopen events. The previous verification checked service reuse before cold start, missing the cold-start-then-reopen sequence. Those individual historical passes do not establish repeat-open correctness.

The installer now uses a tested command that redirects the entire background group and replaces its shell with the worker through `exec`. The real `/bin/sh` regression performs two opens, requiring each captured command to return while its worker remains alive through a private Unix socket handshake; it also checks literal quoted paths, cwd, PATH and both log streams. Focused launcher tests **7/7 PASS** and independent read-only review found no code blocker. Full verification **189 files / 4,839 tests PASS**, four workers, 547.63 seconds; public hygiene, lint, typecheck, build and compiled daemon/operator E2E PASS, zero real model turns or target writes. The first focused attempt was denied at the Unix-socket listener by the sandbox before assertions; one unchanged rerun with local-listener permission passed.

The replacement app is installed, retaining its predecessor. The new local signature caused macOS to recheck the existing Documents grant: a narrowly filtered system diagnostic reported a code-requirement mismatch followed by a permission prompt, while the foreground file probe waited in `open`. System Settings still displayed the Console Documents switch as on. Computer use explicitly forbids operating the system notification app, so Hanlin restored the existing grant manually. No TCC database edit or system-protection bypass occurred. Apple's [ad-hoc signing/TCC guidance](https://developer.apple.com/forums/thread/125438) explains why a local rebuild may need renewed recognition; it is separate from the repaired shell defect.

After that grant refresh the old daemon still returned `LOCAL_OPERATION_FAILED` for file-backed page/results reads, while stored task/status reads worked. Its execution, planning and discussion RUNNING counts were all zero. It was stopped normally, and Finder started a fresh daemon with the updated app. Formal HTTP checks then passed for the current delivery, seven retained attempts, four completed subtasks, three dependency edges, three attributed conclusions, exact original result/usage and JavaScript asset. The actual GUI sequence now passes **cold start → reopen → close the newly opened page → double-click reopen**, with the same new daemon for both reopens. Safari showed a fresh connected page after each, then opened project discussion without submitting a turn. No literal computer reboot was tested.

A retained desktop backup had also been opened as a second app with the same bundle identifier. Only that identified obsolete applet was stopped and its bundle moved intact into the private `~/Library/Application Support/Codex Task Console/desktop-entry-backups/` directory. Desktop now has one Console entry. Future installs keep each predecessor in a unique private backup directory after the new bundle passes signature verification; no backup is overwritten. Independent read-only review found no additional blocker, and final lint/public/diff checks passed after this installer-only backup-location adjustment. When replacing the app itself, stop its idle daemon and applet first, preserve task records, and start through the new app after any normal macOS recognition prompt; merely renewing the permission while retaining the old process is insufficient. Ordinary Console builds do not require rebuilding the desktop app.

The entry points at this repository and the installed Node runtime. If either is moved or removed, rebuild/reinstall the entry. Startup uses a private log under `~/Library/Logs/Codex Task Console/launcher.log`. A matching dead process's stale authority can be reclaimed; live or mismatched authority is preserved. A rare simultaneous stale cleanup may require reopening one launcher, without stealing another live service. If a stopped daemon's PID has been reused by an unrelated live process, automatic cleanup conservatively refuses; verified authority recovery is then needed. These are retained low-frequency launcher limitations, not a claim of universal restart recovery.

Schema 29 adds settings, idempotency and presentation metadata. Migration runs with foreign-key restoration and integrity checks. Keep a private schema-28 backup before activation. For rollback, stop the exact Console daemon, preserve the current database separately, restore the backup with the matching older binary, and reinstall its entry; never open a migrated database with an old binary or delete history to force compatibility.
