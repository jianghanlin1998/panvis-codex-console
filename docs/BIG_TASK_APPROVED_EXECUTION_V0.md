# Human-approved Big Task execution V0 (Step 9C)

This bounded slice extends Step 9B's live planning and the existing governed role engine. AI plan approval does not authorize target execution. The operator must first show Hanlin the exact reviewed plan, scope, acceptance and limits; record his confirmation; then start execution. Ordinary model calls within that approval do not require repeated conversational consent. Product changes, changed source or limits, uncertain runs and final product acceptance remain human boundaries.

## Operator contract

- `execution-review <bigTaskId>`: exact candidate/contracts, plan digest, source HEAD and execution-readiness issues. Read-only; no provider call or target mutation.
- `execution-approve <json-file>`: immutable `{bigTaskId, planDigest, repositoryHeadSha, limits}`. Limits contain `durationMilliseconds` (at most three hours), `totalTokenLimit` (at most 2,880,000), `roleCallLimit` (at most 192), and `repairCycleLimit` (1 or 2). Reject stale plans, impossible dependency profiles and two-repair plans without writable HIGH_RISK_FOUNDATION tasks. Approval alone does not start execution or create target worktrees.
- `execution-start <bigTaskId>`: returns promptly, then drives existing governed roles serially in the local daemon. Duplicate starts cannot duplicate provider claims. At most four Big Task workers may be present; existing project and worktree capacity rules still apply.
- `execution-status <bigTaskId>` and `execution-pause <bigTaskId>`: inspect or stop a worker. Known token totals are separate from active calls and unknown completed usage. Missing usage is never represented as complete zero usage.
- `execution-accept <json-file>`: `{bigTaskId, headSha}` confirms only the exact integrated result after automated completion. Hanlin may inspect/check out the result first. This operation does not merge, push or deploy it.

Fixed authenticated localhost POST routes use `/v0/execution/{review,approve,status,start,pause,accept}`. Existing strict JSON, body, response, origin and authentication boundaries apply. No shell commands, paths or network permissions may be supplied through these endpoints. Existing endpoints do not accept model options; the explicit recovery endpoint below accepts only its fixed Sol/xhigh policy.

## Candidate and recovery guarantees

A separate `codex/execution/<digest>` result branch accumulates completed, proven candidates. Each new owned task worktree starts from that result, while the source checkout and its original HEAD stay unchanged. Model tools write only their authorized candidate files. The coordinator creates commits using a private Git index, fixed identity, explicit parent, disabled hooks and raw file hashing and compare-and-swap branch updates. Effective local, included or worktree filter configuration is rejected before coordinator content operations; filtered repositories are unsupported in this slice. It never executes repository hooks or filters, pushes, merges main or rewrites working files.

Integration stores its exact intent before updating Git and records completion afterward. A repeated integration can reconcile only that exact intent and SHA. Ref drift, missing proof and changed source stop execution. Regular files are bounded to 10,000 paths and 64 MiB per candidate; unsupported links or filesystem objects fail closed. Interrupted model work and its worktree remain available for diagnosis; no automatic reset or uncertain provider replay occurs. Nested approval-source reads, every governed candidate cleanliness check, worktree provisioning and governed completion release share the execution Git boundary: each command checks current filter configuration and receives a timeout capped by the original remaining duration. Expiry before provisioning or governed removal, including after ID generation, a reservation or the final removal hook, cannot launch a worktree write. Completion-release failure retains durable reconciliation evidence; it cannot silently advance integration. Partial operations remain blocked for reconciliation.

Pause and restart preserve the original deadline, token totals and role count. A restart between successful roles permits explicit resume from the durable checkpoint. An active or uncertain provider reservation requires human review. Shutdown aborts and drains owned workers. Deadlines cover provider startup and each protocol stage as well as model execution and coordinator candidate/integration Git operations; existing bounded interrupt/child cleanup grace remains additional. Existing per-role idle and absolute limits and per-subtask token caps also remain in force.

Two repair cycles apply only when the immutable execution approval selects two. Legacy workflows keep one. Fresh QA failure can run repair/re-QA twice, stopping on the second failed re-QA. Each later repair carries all earlier blocking findings plus new blocking findings (at most two batches, 32 targets); historical provider claims stay bound to the findings available before their exact role sequence. Only successful focused QA can resolve those findings.

The forward migration reconstructs five counter-constrained tables with every historical row, index and dependent trigger preserved. SQLite foreign-key enforcement is suspended only during migration initialization; the migration checks foreign keys before committing, and storage enables and checks them again after actual migration before exposing runtime access. Reopening an already-migrated database retains the established scoped-corruption behavior: affected reads fail closed while unrelated tasks remain accessible. Append-only execution evidence and governed schema fingerprints are checked on reads.

## Delivery and current real-plan boundary

`AWAITING_ACCEPTANCE` means the governed task graph completed and every candidate was integrated. It does not mean Hanlin accepted the product, or that offline model roles fetched real publisher news. Execution roles retain network-disabled sandboxes. Actual news fetching and visual product checks must be demonstrated during the separately approved Board run and final product verification; synthetic tests do not satisfy those claims.

The existing four-task AI Update Board plan is preserved. Its STANDARD upstream tasks cannot satisfy its ACCEPTED dependency gates; it requires a corrected, freshly reviewed plan before execution approval. Its final read-only verification task also cannot perform automatic code repairs. Do not silently rewrite that candidate, reset prior attempts, reuse an expired planning exception or claim that implementation has begun. The new review reports this conflict and approval rejects it before target execution.

This slice adds no discussion UI, direct small-task intake, deployment, live network verification runner, automatic budget extension or automatic human acceptance.

## Explicit Sol recovery of one failed implementation

Hanlin approved a task-scoped continuation after the Board's first implementation exceeded its 120K subtask allowance. This amendment preserves the original plan, source, result branch, start/expiry, aggregate token limit, role-call limit, two repair cycles and all historical usage (including cached input). Other tasks and ordinary execution defaults are unchanged.

- `execution-recovery-review <bigTaskId>` is read-only. It returns the exact failed authorization/run, current retained-file digest, plan/source binding, known tokens and original expiry. Only one terminal failed/interrupted writable EXECUTE role with complete usage and no accepted role result can qualify; active or unknown work, source drift, expiry and exhausted aggregate/call limits are rejected.
- `execution-recover <json-file>` records the reviewed request after human authorization. The request fixes `model: gpt-5.6-sol`, `reasoningEffort: xhigh`, and `subtaskBudgetMode: WARNING_ONLY`. There is no arbitrary model, path or limit override. A replay of the identical request is idempotent; any different second request is rejected.
- The recovery adds one authorization at the same workflow stage with a separate immutable identity and run. The old failed attempt remains counted and cannot be replayed. The candidate is retained without an automatic commit or acceptance. Its content digest must still match before the replacement model can start, including if deletion of partial files makes Git clean again.
- `execution-start` resumes from the recorded PAUSED checkpoint. Both thread/start and turn/start explicitly select the requested model/effort; a different model returned by the provider is rejected. No user-wide configuration changes. Subsequent roles in this same Big Task inherit the explicit policy.
- The original aggregate budget remains the hard stopping boundary. Subtask usage is still reported in full, with a 120K warning instead of a separate hard pause. Streaming usage can arrive after a generation step has crossed the remaining allowance; it is retained honestly and stops further execution. Unknown usage still blocks.
- Recovery does not consume or reset QA repair cycles. It permits only one known failed initial implementation recovery, not generic replay of failed QA, uncertain provider calls, or repeated recoveries. All ordinary hardening, fresh QA, integration, and final human acceptance remain required.

Migration 24 adds a default-zero recovery ordinal to role authorizations and extends the uniqueness/immutable-insert guards. Existing rows, links, provider claims and events stay unchanged. The recovery request is append-only execution evidence. Older binaries cannot understand this new evidence/schema; do not downgrade an activated database in place.

Fixed authenticated localhost routes are `/v0/execution/recovery-review` and `/v0/execution/recover`, retaining the ordinary request/response size, origin, token and method checks. Activation requires all repository verification checks first.
