# Human-approved Big Task execution V0 (Step 9C)

This bounded slice extends Step 9B's live planning and the existing governed role engine. Before a new product or material direction change, align with Hanlin on its purpose, concrete success examples, scope and material assumptions. Then show the reviewed implementation plan and record his execution approval. Already granted authorization carries forward: routine tools, model calls, implementation, engineering review and agreed repairs do not need repeated conversational consent. Material product changes, newly expanded authority and final product acceptance remain human decisions.

## Operator contract

- `execution-review <bigTaskId>`: exact candidate/contracts, plan digest, source HEAD and execution-readiness issues. Read-only; no provider call or target mutation.
- `execution-approve <json-file>`: immutable `{bigTaskId, planDigest, repositoryHeadSha, limits}`. Limits contain `durationMilliseconds` (at most three hours), `totalTokenLimit` (at most 2,880,000), `roleCallLimit` (at most 192), and `repairCycleLimit` (1 or 2). Reject stale plans and impossible dependency profiles. Two-repair plans require writable reviewed tasks: HIGH_RISK_FOUNDATION, or STANDARD for the new confirmed-product intake described below. Approval alone does not start execution or create target worktrees.
- `execution-start <bigTaskId>`: returns promptly, then drives existing governed roles serially in the local daemon. Duplicate starts cannot duplicate provider claims. At most four Big Task workers may be present; existing project and worktree capacity rules still apply.
- `execution-status <bigTaskId>` and `execution-pause <bigTaskId>`: inspect or stop a worker. Known token totals are separate from active calls and unknown completed usage. Missing usage is never represented as complete zero usage.
- `execution-accept <json-file>`: `{bigTaskId, headSha}` confirms only the exact integrated result after automated completion. Hanlin may inspect/check out the result first. This operation does not merge, push or deploy it.
- `execution-close <json-file>`: `{bigTaskId, headSha, reason}` records Hanlin's explicit decision to close a delivered workflow without product acceptance. It moves only AWAITING_ACCEPTANCE to CLOSED and retains `closeout: {at, reason, productAccepted: false}`. Same-request replay is idempotent; changed reasons, wrong result SHA, unfinished work and later automatic acceptance are rejected. Closed tasks cannot restart provider work. A waiver is not a passing test.

Fixed authenticated localhost POST routes use `/v0/execution/{review,approve,status,start,pause,accept,close}`. Existing strict JSON, body, response, origin and authentication boundaries apply. No shell commands, paths or network permissions may be supplied through these endpoints. Existing endpoints do not accept model options; the explicit recovery endpoint below accepts only its fixed Sol/xhigh policy.

## Candidate and recovery guarantees

A separate `codex/execution/<digest>` result branch accumulates completed, proven candidates. Each new owned task worktree starts from that result, while the source checkout and its original HEAD stay unchanged. Model tools write only their authorized candidate files. The coordinator creates commits using a private Git index, fixed identity, explicit parent, disabled hooks and raw file hashing and compare-and-swap branch updates. Effective local, included or worktree filter configuration is rejected before coordinator content operations; filtered repositories are unsupported in this slice. It never executes repository hooks or filters, pushes, merges main or rewrites working files.

Integration stores its exact intent before updating Git and records completion afterward. A repeated integration can reconcile only that exact intent and SHA. Ref drift, missing proof and changed source stop execution. Regular files are bounded to 10,000 paths and 64 MiB per candidate; unsupported links or filesystem objects fail closed. Interrupted model work and its worktree remain available for diagnosis; no automatic reset or uncertain provider replay occurs. Nested approval-source reads, every governed candidate cleanliness check, worktree provisioning and governed completion release share the execution Git boundary: each command checks current filter configuration and receives a timeout capped by the original remaining duration. Expiry before provisioning or governed removal, including after ID generation, a reservation or the final removal hook, cannot launch a worktree write. Completion-release failure retains durable reconciliation evidence; it cannot silently advance integration. Partial operations remain blocked for reconciliation.

Pause and restart preserve the original deadline, token totals and role count. A restart between successful roles permits explicit resume from the durable checkpoint. An active or uncertain provider reservation requires reconciliation. Shutdown aborts and drains owned workers. Deadlines cover provider startup and each protocol stage as well as model execution and coordinator candidate/integration Git operations; existing bounded interrupt/child cleanup grace remains additional. Within an approved Big Task, each model turn uses the remaining approved parent window instead of an extra 20-minute ceiling. The five-minute idle limit still refreshes only on validated exact-turn activity; active work cannot extend the parent deadline. Standalone roles without a parent approval retain their bounded absolute fallback. Existing token policy and its explicitly recorded warning-mode amendments remain authoritative.

Two repair cycles apply only when the immutable execution approval selects two. Legacy workflows keep one. Fresh QA failure can run repair/re-QA twice, stopping on the second failed re-QA. Each later repair carries all earlier blocking findings plus new blocking findings (at most two batches, 32 targets); historical provider claims stay bound to the findings available before their exact role sequence. Only successful focused QA can resolve those findings.

The forward migration reconstructs five counter-constrained tables with every historical row, index and dependent trigger preserved. SQLite foreign-key enforcement is suspended only during migration initialization; the migration checks foreign keys before committing, and storage enables and checks them again after actual migration before exposing runtime access. Reopening an already-migrated database retains the established scoped-corruption behavior: affected reads fail closed while unrelated tasks remain accessible. Append-only execution evidence and governed schema fingerprints are checked on reads.

## Activity and usage reporting (2026-09-08)

Execution status adds optional `activeRole` with the exact run/subtask/role, `usageState: IN_PROGRESS`, and recent progress when available. Progress contains only the trusted observed time, coarse activity category, tool/notification counts and normalized partial usage. It excludes raw prompts, chats, commands, paths and provider errors. Unchanged progress is throttled; missing/stale display telemetry cannot interrupt the model. It never changes final usage or debits the budget twice. `usageBreakdown` reports settled input, cached input, output and reasoning tokens with per-field missing-run counts; cached input/reasoning are subsets, and `TOKENS_NOT_CURRENCY` explicitly excludes a monetary estimate.

Migration 27 adds only the latest execution-progress table. CLOSE is append-only event evidence in the existing table. Back up private state before activation; do not reopen a database containing CLOSE evidence with an older binary. Rollback requires a verified compatible binary or a matching pre-activation backup, retaining the newer database separately. Do not delete or edit history to resume work.

### Explicitly approved replacement time windows

After an approved window expires, `execution-renew-window <json-file>` can record the next explicitly approved window of at most three hours. Its strict request contains `bigTaskId`, `planDigest`, `previousExpiresAt` and `durationMilliseconds`. It requires a stopped PAUSED or HUMAN_REQUIRED state, the exact current expiry and plan/source, settled usage (allowing only an already acknowledged unknown), remaining call budget and any applicable hard token budget, and no pending integration. It does not start a model or accept unfinished work.

Each append-only `WINDOW_RENEWED` event binds the immediately preceding effective expiry, including a prior QA recovery window. The original approval, start, failed runs, usage, model, repair allowance and all older deadlines remain intact. Status keeps the first record in `windowRenewal` and later records in optional `additionalWindowRenewals`; `expiresAt` is derived from the ordered amendment history. Identical historical replay returns the current state without extending time; a changed duration for the same previous expiry is rejected. No automatic renewal or token increase is provided. An interrupted initial role still needs the existing exact-candidate recovery before execution can restart; a TIME_LIMIT_REACHED stop at a safe checkpoint can restart directly after renewal. New unknown usage and active calls remain blocking. The authenticated route and request limits are unchanged. No schema migration is needed, but older binaries cannot replay repeated renewal events and must not reopen an amended database.
